## 1. Executive Summary & Why Member 4 Started First

In a distributed web project sharing a real-time cloud database (Firebase Firestore), **Member 4 does not need to wait for others**. In fact, building the database schemas, connection layer, notification system, and mock test harness first is **industry standard best practice**.

By establishing this foundation up front:
1. All members agree on **exact database collection names and field names**, preventing costly mismatches later.
2. Members 2 and 3 can write logic directly against a verified Firestore configuration (`firebase-config.js`).
3. Member 1 knows the exact **DOM IDs and CSS classes** required by JavaScript logic.
4. Member 4 has provided `test-integration.html`, a self-contained testing workbench to verify database sync, audio chimes, mobile vibration, and push notifications independently.

## 3. Database Contract (Firestore Schemas)

All team members **must strictly use** these collection names, document IDs, and field names:

### Collection 1: `counters`
*Stores the current operational state of each canteen counter.*

- **Document ID:** `CANTEEN01` (Default for single-counter MVP)
- **Document Fields:**
  | Field Name | Type | Example | Description |
  | :--- | :--- | :--- | :--- |
  | `counterId` | `string` | `"CANTEEN01"` | Primary counter identifier |
  | `counterName` | `string` | `"College Canteen Counter 1"` | Display name |
  | `currentToken` | `string` | `"A105"` | Token currently being served (or `"---"`) |
  | `currentCustomerName` | `string` | `"Sakshi"` | Name of the customer currently at counter |
  | `isActive` | `boolean` | `true` | Operating status of the counter |
  | `updatedAt` | `timestamp` | `serverTimestamp()` | Last updated timestamp |

### Collection 2: `queues`
*Stores every individual customer token and status in the queue.*

- **Document ID:** Auto-generated by Firestore (`db.collection('queues').add(...)`)
- **Document Fields:**
  | Field Name | Type | Allowed Values | Description |
  | :--- | :--- | :--- | :--- |
  | `tokenId` | `string` | `"A101"`, `"A102"`, etc. | Human-friendly token number |
  | `counterId` | `string` | `"CANTEEN01"` | The counter this customer joined |
  | `customerName` | `string` | `"Sakshi"` | Customer name entered on joining |
  | `status` | `string` | `'waiting'` \| `'serving'` \| `'completed'` \| `'skipped'` \| `'cancelled'` | Status lifecycle enum |
  | `createdAt` | `timestamp` | `serverTimestamp()` | Ordering key for queue position |
  | `servedAt` | `timestamp` | `serverTimestamp()` | When admin called this token |
  | `completedAt` | `timestamp` | `serverTimestamp()` | When counter marked served |
  | `cancelledAt` | `timestamp` | `serverTimestamp()` | When customer left queue |

> **Critical Rule:** Position is **dynamically calculated** based on how many `waiting` entries have an earlier `createdAt` timestamp. Do not hardcode position in the database.

### Member 2: Queue Management (Core Logic)
**Owns:** `js/queue.js`, `js/admin.js`

#### JavaScript API Contract (`window.LineAlertQueue`):
```javascript
// 1. Add customer to queue
const queueItem = await LineAlertQueue.addCustomerToQueue(counterId, customerName);
// Returns: { id: docRef.id, tokenId: 'A102', customerName: 'Rahul', status: 'waiting', ... }

// 2. Call next waiting customer
const calledCustomer = await LineAlertQueue.callNextCustomer(counterId);
// Moves oldest 'waiting' to 'serving' and sets previous 'serving' to 'completed'.

// 3. Complete or Skip
await LineAlertQueue.markCurrentAsServed(counterId);
await LineAlertQueue.skipCurrentCustomer(counterId);

// 4. Reset queue
await LineAlertQueue.resetQueue(counterId);

// 5. Subscribe to Real-time streams
const unsubscribe = LineAlertQueue.subscribeToActiveQueue(counterId, (activeItems) => {
  // activeItems contains array of all currently 'waiting' and 'serving' documents
});
```

#### Local Storage Contract (Customer Session Persistence):
To prevent a user from losing their token on page refresh, use these standardized keys:
- `localStorage.setItem('linealert_token_id', tokenId)`
- `localStorage.setItem('linealert_doc_id', docId)`
- Clear both upon clicking `#btnLeaveQueue` or when token is marked completed.

### Member 4: Notifications, Database & Deployment (Integration Lead)
**Owns:** `js/firebase-config.js`, `js/notification.js`, `firebase.json`, `test-integration.html`

#### JavaScript API Contract (`window.notifier`):
```javascript
// 1. Request Browser Notification Permission
const status = await window.notifier.requestPermission(); // 'granted' | 'denied'

// 2. Synthesized Web Audio Chimes (Zero external MP3 dependencies!)
window.notifier.playChimeTone('approaching'); // 2-tone melodic chime
window.notifier.playChimeTone('serving');     // 4-tone urgent fanfare
window.notifier.playChimeTone('success');     // Upbeat confirmation
window.notifier.playChimeTone('cancel');      // Descending cancel tone

// 3. Tactile Mobile Vibration
window.notifier.triggerVibration([200, 100, 200]);

// 4. High-Level Trigger
window.notifier.notifyTurnApproaching(2, 'A105'); // 2 people ahead
window.notifier.notifyNowServing('A105', 'College Canteen'); // It's your turn!

// 5. Automatic Queue Position Evaluator (Anti-Spam)
window.notifier.processQueuePositionChange(queueDocData, peopleAhead);
```

## 5. Git Collaboration & Branching Strategy

Follow this Git workflow to prevent merge conflicts:

1. **Repository Setup:**
   ```bash
   git init
   git branch -M main
   ```
2. **Individual Branches:**
   - Member 1: `git checkout -b feature/member1-ui`
   - Member 2: `git checkout -b feature/member2-queue-logic`
   - Member 3: `git checkout -b feature/member3-qr-customer`
   - Member 4: `git checkout -b feature/member4-database-notifications`
3. **Merging Rules:**
   - Test locally with `test-integration.html` before creating a pull request.
   - Do not rename shared DOM IDs or Firestore fields.

## 6. How to Deploy to Firebase Hosting

1. Install Firebase CLI (if not already installed):
   ```bash
   npm install -g firebase-tools
   ```
2. Login to Google account:
   ```bash
   firebase login
   ```
3. Associate with your project:
   ```bash
   firebase use --add
   ```
   Select your project (e.g. `line-alert-demo`).
4. Deploy the application:
   ```bash
   firebase deploy --only hosting,firestore:rules
   ```
5. Your live URL will be: `https://<YOUR-PROJECT-ID>.web.app`.

## 7. Step-by-Step Teacher Demonstration Guide

When presenting to your professor:
1. **Setup Two Windows Side-by-Side:**
   - **Window 1 (Laptop):** Open `admin.html` (Counter Operator).
   - **Window 2 (Mobile / Incognito):** Open `index.html` or scan the QR code to open `customer.html`.
2. **Step 1 — Show QR Code:**
   - Point out that the counter displays a dynamic QR code.
3. **Step 2 — Join Queue:**
   - Enter name "Sakshi" in `customer.html` and click **Join Queue Now**.
   - Show that token `A101` is instantly generated and appears in the Admin's live queue table in real-time.
4. **Step 3 — Demonstrate Queue Position:**
   - Add 2 more test customers (e.g. "Rahul", "Priya") via `test-integration.html` or another browser tab.
   - Show how "People Ahead" and "Estimated Wait Time" update dynamically.
5. **Step 4 — Demonstrate "Turn Approaching" Notification:**
   - Admin clicks **Call Next Customer**.
   - When the customer's position reaches 2, demonstrate the **audio chime** and browser notification banner!
6. **Step 5 — Demonstrate "Now Serving":**
   - Admin calls the customer's token.
   - Show the **urgent 4-note chime**, device vibration, and **"It's Your Turn!"** red badge.
7. **Step 6 — Live Firebase Hosting URL:**
   - Open the live URL on your smartphone over cellular data to prove true wireless mobile computing!
